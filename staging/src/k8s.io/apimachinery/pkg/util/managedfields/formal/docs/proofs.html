The ownership contract

      
A manager is full for one item when it claims that item's membership and its entire recursively required core. The same manager must cover every required object branch. Optional nested items have their own lifetimes and can have different full managers.

      
For a key-only item, every membership claimant is full. Last-claim deletion follows the same lifetime rule. A full child does not protect a deleted ancestor.

    

    

  

  

    
Values can remain valid while ownership breaks

      
Schema: items is an associative list keyed by name; host and port are required. Bold means required; underlined bold means key.

    

    

      
1
A applies a complete item

        
items:
- name: database
  host: db.example.com
  port: "5432"

        
A is full.

      

      
2
B co-claims only port

        
items:
- name: database
  port: "5432"

        
A remains full. B is partial.

      

      
3
A tries to release port

        
items:
- name: database
  host: db.example.com

        
Rejected: no full manager would remain.

      

    

    
Why the value check is insufficient

      
B still claims port, so both values remain in the candidate. But A would own only host and B only port. The full-manager invariant requires an individual witness, not a coalition. Rejection retains A's original port claim.

      
A handoff first has B acquire the entire required core. Only then can A release it while B remains full.

      

    

  

  

    
1. The shape predicate is too weak

      
The current flat-cell representation can simultaneously mark foo as a scalar and store foo.bar. No valid object tree can have both. The current shapeValid predicate checks item ancestors and unique paths, but does not forbid descendants under atomic values.

      
The theorem accepted_valid still correctly preserves that predicate. A stronger representation invariant, or a recursive tree representation with an appropriate encoding proof, is an open obligation.

      
    

    
2. Synthetic presence claims change later pruning

      
A applies settings.left: one. B force-transfers it to two, then applies an empty configuration. The current normalization gives A an additional object-presence claim.

The implementation comparison executes both outcomes and records this exact difference as model-gap. It is a known defect or normalization mismatch, not an intended full/partial semantic change.

    

    
Other open boundaries

      
General handoff progress, arbitrary schema normalization, Go refinement, Update, version conversion, defaulting, CEL, admission webhooks, and storage concurrency are outside the completed proof claims. Required granular collection presence is an explicit design assumption that current SMD field sets do not fully preserve.
